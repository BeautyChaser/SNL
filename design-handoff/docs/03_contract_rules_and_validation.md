# 03 — 契约、可判定性与校验规则

## 三类不同强度的声明

**A. 可机器判定 (machine-checkable)**：Schema 格式、必需字段、类型/枚举/单位一致性、ID/引用解析、授权路径、已定义端口的兼容性、数值断言（若有可靠执行器）、带确定预期结果的测试等。

**B. 依赖验证证据 (test-backed)**：性能阈值、数值误差、流程输出是否符合业务目标、重试行为、数值模型与参考解的一致性。通过测试/基准/验证案例实现证据；仅有测试名而未执行时不能声称已验证。

**C. 需人工审查 (review-required)**：例如“合理”“鲁棒”“误差足够小”，或业务真值不足以判断的自然语言条款。可发出警告、要求补全可测条件，不得直接判为 PASS。

每条验收应有稳定 ID、表达、检查类别、验证依据、状态；MVP 可只实现检查类型与关联，无须自造完备逻辑推理器。

## MVP 结构检查

- 根文档合法、`snl_version` 和 `kind/id/status` 可识别；schema 版本不兼容时明确拒绝或提示迁移。
- YAML 安全解析、非空字符串要求、必需字段与值类型/枚举限制。
- 重复 ID、重复 step ID、重复输出端口明确报错，错误报告含 source path 和稳定 ID。
- 多文件内引用缺失或同名歧义报错。
- `APPROVED` 与 `DRAFT/OPEN` 在 IR 和 `pack` 中保留语义状态，不因读取时的默认值变成 Approved。

## MVP 组合/语义检查

- 依赖是否可达、类型/kind 是否适配、输入输出端口是否存在、声明类型是否兼容。
- 若声明 `owner/write_access`，不能同时出现两个互相冲突且无协调的“唯一写者”。
- 写路径、文件输出与副作用须声明（若尚未完整语义支持，报告 `NOT_IMPLEMENTED` 而非 PASS）。
- Workflow 步骤的 `next`/`branch` 引用完整且可追溯；无显式出口的闭环应诊断。允许具退出条件/最大次数的显式循环，而非一刀切拒绝所有环。
- 分支覆盖性、条件重叠、优先级等仅在条件是**形式化、可判定**时做自动证明；对于自然语言 `when` 发出 `REVIEW_REQUIRED` 并显示出原文。
- 状态为 `OPEN` 的必需接口/行为不得无提示地进入“已审定可执行”构建视图。

## 可观察行为

要求公开接口可观察：有输入和输出定义，错误类别，明确副作用。典型反例：只声明“负责参数处理”而没有输入/输出/异常/可检测性。行为步骤可以用报告式中文写，但关键分支的实际条件应逐步补充可验证表达。

## 诊断格式（建议）

每条诊断至少有：`code`、`severity`（error/warning/info/review_required）、`message`、`source_path`、`definition_id`、`step_id`（可缺）、`related_refs`、`suggested_action`。CLI 进程退出码建议：0=通过（可能含可接受 warning），2=存在错误，3=输入/环境/运行失败；不要把 warning 隐藏。

JSON 输出和人类可读输出都需稳定排序，方便 CI 比对和 Git Diff。

## 测试不是规约本身

测试可以检验某个条件，但测试通过并不推出对所有输入均正确。可自动验证的契约集合应随项目演进扩大；失败/测试空缺必须暴露。SNL 是把可验证的部分与未决的部分分离的基础设施，不是把未知语义藏到 AI 模型“相信自己正确”的机制。
