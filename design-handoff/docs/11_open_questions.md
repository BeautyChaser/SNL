# 11 — 开放问题与需要真实实验决定的边界

将本文件作为 SNL 的 Living Specification 测试素材：允许 AI 提出变更和验证方案，不把所有问题在第一天靠猜测定案。

| Q-ID | 问题 | 对 MVP 的处理 |
|---|---|---|
| Q-01 | SNL 是否永久使用 YAML，还是需要领域定制简写/Markdown 段落？ | 暂用严格 YAML 子集与自然语言字符串；保证 schema_version 与迁移能力 |
| Q-02 | 如何声明表达式/单位/兼容关系而不引入不安全执行？ | MVP 只支持基本字符串类型与端口匹配；不可判定条款标 REVIEW_REQUIRED |
| Q-03 | 审批身份如何可信，能否融入 PR/MR、签名和组织权限？ | MVP 不提供虚假可信审批；保留状态/基线/内容哈希与记录接口 |
| Q-04 | 局部条款审定后被跨章节编辑影响，如何自动检测影响闭包？ | 先结构依赖传播 + 人工复核，逐步做影响分析 |
| Q-05 | 静态 Scope 是否足以保护 Agent？ | 不能；MVP 检测 Git 差异，硬约束依赖受限工具/环境 |
| Q-06 | 上下文预算如何按不同模型准确估算与压缩？ | MVP 明确使用估计，精确 tokenizer 按适配器扩展 |
| Q-07 | 黑箱局部解构如何建模状态迁移与运行时等价？ | 先用 opaque + extracted 引用/契约/证据，不伪造等价证明 |
| Q-08 | GitLab Knowledge、SNL、源码多仓版本怎样同时锁定？ | MVP 记录 source/knowledge/version refs，不内置全功能 RAG |
| Q-09 | `snl verify` 执行哪些测试？如何隔离任意命令？ | MVP 不默认执行任意远程/用户提供脚本；先检查测试引用和选择性可信本地命令 |
| Q-10 | 用户修改被 AI 草拟的 Open/Draft 时如何保留作者/来源与争议？ | 版本化 Change Proposal + Git diff；长期考虑审计与冲突解决 |
| Q-11 | Entity 的 Owner 与项目文件写权限是否同一概念？ | 不是；分别定义软件状态所有权和开发操作 Scope |
| Q-12 | 应否做开放式代码生成器、GUI、Agent 运行时？ | 先做 CLI/IR/验证；以上不是 MVP 前提 |
| Q-13 | 具体开源许可证选择、项目名称和发布渠道？ | 保留待定，不未经批准声称已采用特定许可证 |
| Q-14 | 合法分支条件覆盖的静态求解范围多大？ | 自然语言条件不能普遍自动证明；逐步引入安全的结构化条件/求解器 |

建议每个问题在项目内留稳定 ID、当前状态、备选方案、实验记录、受影响契约和人工决议引用。这也是 SNL 本身必须支撑的开发体验。
