# 07 — 像写报告一样写模块：可追溯的步骤、分支与异常

## 出发点

自然语言对模块的表达不必变成源代码伪语法，也不应只写泛泛的功能简介。它可以像一份逻辑清晰的技术报告/多文件讲演稿：先定义任务，再依序编号步骤、分支、合流、异常、证据与未决问题，最终指导 Agent 实现。

## 建议模块报告结构

1. **目标和边界**：意图、受众/Agent 角色、上下文、哪些行为不属于本模块。
2. **公开接口**：输入/输出、类型/单位、默认行为、前后置条件、可观察副作用。
3. **行为步骤**：稳定步骤 ID（`S1`、`S2.1` 等）；每步是 `action / decision / merge / loop / error / exit` 等候选种类。
4. **条件分支**：每个判断显式声明条件、优先级（若必要）、互斥/覆盖情况、默认分支及不满足时怎么办。条件自然语言化而未形式化时必须提示需要 review。
5. **循环**：循环入口、继续/退出条件、最大次数/超时/失败分支，避免不受约束的执行环。
6. **异常**：错误类别、触发条件、应输出的可定位消息、是否允许恢复重试。
7. **验收**：正反案例、可检查表达、预期输出、证据来源、步骤 ↔ 测试引用。
8. **未决点和审定范围**：AI 不得凭常识给未决条件补写确定业务规则。

## 参数预处理模块案例（重点）

- 输入：原始用户配置、规则或补充值来源（实验、计算、辨识）和约束；输出：规范化配置、参数来源记录、校验报告/错误。
- 分支：合法显式输入应保留；非法显式输入应拒绝或按已审定策略处理；缺失但有可信补全来源时补足并标记来源；无法补足时明确报错或保留待决状态，不凭空制造值。
- 顺序：可能需要“基础结构校验 → 缺失字段识别/补全 → 全量范围与一致性校验”，但该顺序也是可以通过实例测试、版本变更调整的，不能从第一次想象一劳永逸。
- 验收：不会覆盖合法输入；每个自动补全值有可追踪来源；坏值错误指向具体字段；不可补全时不生成虚假参数；输出确定性与幂等性（当业务策略明确需要时）。

## 为什么需要稳定步骤 ID

若只在 Markdown 中写“第三步”，插入新步骤就会导致所有追溯引用漂移。稳定 ID 有利于构建 `SNL Step ↔ Source Function/Module ↔ Test Case ↔ Evidence`，对改动展示 Delta 和影响，并在图中定位单个分支。

## 可验证性分层

工具可机器验证 **分支引用完整性**，但在一般自然语言描述下无法证明两个条件互斥或涵盖所有情况。对分支条件采用 `checkability: machine | test | review`，未形式化的分支应产出 `REVIEW_REQUIRED`，而非报“自动证明分支完备”。

## “演讲稿”类比的真正技术含义

不同 Agent 任务需要不同的“讲稿”：实现 Agent 需要模块接口、局部约束、文件范围和测试；Tester 需要契约及失败模式；Architect 需要依赖/组合/变更影响。SNL 既要保持内容正确，也要按角色、上下文预算分发，不能把所有历史对话一股脑塞入上下文。
