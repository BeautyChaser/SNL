# 04 — Living Specification：共同编辑、局部审定和受控演化

## 方向性设计

规约的真实功能是**承载探索与逐步收束**。最开始的自然语言想法可以不完整、错误或冲突。人和 Agent 都允许提案、查阅、编辑与删除草案，也允许通过测试或用户反馈推翻此前判断。和“先锁死规约然后叫 AI 执行”不同，写规约与编码/测试会双向促进。

## 最小状态模型（候选枚举）

- `OPEN`：问题/内容尚无确定定义，可能包含多个候选。
- `DRAFT`：可供实验/实现的暂定草案，但不代表正式认可。
- `APPROVED`：**特定版本/特定范围**已由人类或获得授权的治理流程明确批准。
- `SUPERSEDED`（后续）：旧版本被后继批准定义替代，但历史仍保留。

**局部审定**：整体文件可仍是 DRAFT，但输入输出某些段落已批准；审批单位须标记范围（如 `/interface/inputs`、`/contracts/C-01`）和基于的版本/内容哈希。不能把“文件里有一项 APPROVED”偷换成整个模块已审定。

第一版可以用**文件级状态 + 显式待决项 + 已批准的只读快照**实现闭环，再迭代到条款级审核。不能因为实现简化就把开放问题和审定概念整体删除。

## 基线与草案共存

- **effective/baseline view**：在某个确定版本下，已批准且未被替换的定义；可用于有约束的正式实现。
- **working/proposed view**：人和 AI 正在共创、实验的当前版本，允许不完整、矛盾以及对基线的变更提案。
- 同一声明的拟议修订没有获批前不得自动覆盖有效基线。工具输出须显示来源视图与内容哈希，不制造虚假“已批准”。
- 可以在分支上实验；Git commit/Tag 是追溯载体，**不是自动等价于业务批准**。

## 变更生命周期

`Issue/Observation → Proposal → Delta (ADD/MODIFY/REMOVE/RENAME) → Diff + Impact → Tests/Experiment → Human Decision → New Baseline/Reject/Rework → Trace`。

每个 Change Proposal 应记录：修改者/AI 建议者、动机、被修改 ID、预期效果、影响范围、兼容性、证据、待确认项、审定结果和历史引用。影响分析能确定机械依赖，但无法总是自动确定业务影响；这种情况显式要求人工 review。

## 实现中的底线

- 工具不得调用模型生成“看起来已批准”的签名或将 DRAFT 自动 upgrade 为 APPROVED。
- 人工批准可在 CLI/文件/PR 流程发生，但每次必须附审定者、审定对象、原版本/哈希、时间与记录方式；仅简单 `approve --yes` 不代表拥有可信身份。
- 合理 MVP 是先提供 `diff` 和 `review-required` 报告；高级 `approve/impact/migrate` 可以逐阶段实现。
- 删除和重命名要可追溯，不能把 ID 不见了就当“不影响别的模块”。
- 变更后要重新验证依赖以及对应已批准的契约，必要时回滚或升级。

## 验证场景

参数预处理模块最初设计为“先对原始输入做全面校验，再补缺省”；实验发现某些缺失字段应先补充后才能做完整一致性校验。Agent 提出变更和证据，人评估影响并更新分支条件和验收。保留旧版本和测试；只有新规则经确认才替换旧生效基线。这才是“活规约”的实际工程含义。
