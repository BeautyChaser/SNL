# 参数预处理的报告式自然语言规约（教学样例，草案）

**规格 ID**：`example.parameter_preparation`  
**状态**：DRAFT（业务来源优先级、分支覆盖尚待审定）  
**阶段性作用域**：参见 `scope.yaml`。

## 任务意图

将前端提供的缺省电池模型配置与补充实验/辨识/计算规则转成后端可验证的参数集合。SNL 仅记录**期望接口及可观察行为**，不规定如何写 Python 函数、是否采用 Pydantic，也不限定求解器。

## 输入/输出

- 输入：`raw_config`（对象）、`completion_rules`（带可信来源的规则对象）。
- 输出：`normalized_config`（规范化对象）、`validation_report`（字段状态、来源、错误/未决列表）。
- 副作用：默认不写外部文件；若实现确需持久化，应新增并审定其副作用契约。

## 编号步骤

**S1.1 输入结构检查**：判定能否解析配置与规则对象；若不能，返回 `ERR-STRUCTURE`（示例错误码待审定）。

**S1.2 缺失分类**：遍历必需参数，区分显式合法、显式非法、缺失可补、缺失不可补。

**S1.3 条件分支**：
- **B1 显式合法**：保留其值，不被猜测的默认值覆盖。
- **B2 显式非法**：返回可定位错误；不得在未经同意的策略下静默“纠正”。
- **B3 缺失有可信来源**：依据有效补全规则获取值，标记来源、版本及计算/辨识方法。
- **B4 缺失无可信来源**：保留未决或失败状态，不创造虚假参数。

**S1.4 全量校验**：对补足后的数据做范围和交叉字段一致性检查，报告每条违反项。任何“充分合法”的主张需有清晰可判定规则或回归证据。

**S1.5 输出**：产出最终配置及验证/来源报告；如果必需字段存在错误，不得向下游伪装成完整合法工况。

## 验收

- `T-KEEP-EXPLICIT-001`：合法显式参数保持不变。
- `T-PROVENANCE-001`：每项补充值有可追踪来源。
- `T-NO-FABRICATION-001`：不具有来源的必需参数无法补足时报告错误。
- `T-INVALID-VALUE-001`：值超出业务约束时错误指向正确字段。
- `T-DETERMINISM-001`：固定输入/版本/规则条件下输出稳定（需由业务确认对随机算法的处理）。

## 未决条件

- 补充来源优先级、不同辨识方法的冲突处理。
- 输入数据发生单位歧义时如何处理。
- 在业务中是否允许 warning 继续下游运行。

这些未决条款需要由 Agent 提案、人确认和测试证据逐步收束，不可在实现时直接假定。
